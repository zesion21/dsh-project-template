# 中文方案与文档编写（Skills Doc Writer）

<!-- doc-lint-rules-only -->
<!-- 本文件是写作规则文档，正文里必然出现禁用词与反例：整篇跳过 doc-lint.mjs 的词表检查，保留节奏、残留、结构检查。 -->

## 这个技能做什么

写一份**能送到评审桌上**的中文方案类文档：每个论点后面有事实，每个取舍后面有理由，每个数字后面有来源，读起来像是熟悉这个项目的人写的。

三条底线，优先于任何写作技巧：

1. **有依据**：用户提供的材料 > RAG 知识库 > 联网检索 > 明确标注的假设。四者都拿不到的关键条件，问用户。
2. **有信息**：删掉一句话不损失任何信息的，就是废话，删。见 `references/anti-slop.md`。
3. **像人写的**：用词、句式、段落节奏都要避开 AI 的默认输出习惯。见 `references/anti-slop.md`。

## 适用与不适用

| 适用                                          | 不适用                                                                  |
| --------------------------------------------- | ----------------------------------------------------------------------- |
| 技术方案、项目建议书、可研报告、投标技术方案  | 公众号文章、营销文案（用 `skills-wechat-article-writer`）               |
| 需求规格、实施/运维/验收文档、接口与部署说明  | 产品需求文档 PRD（用 `skills-product-manager`，本技能负责技术侧长文档） |
| 项目/产品说明材料、汇报正文、政策申报技术材料 | 演示文稿（用 `skills-ppt-designer`）                                    |

## 起手：信息盘点（先做这一步）

把已知条件分成三类再动手，避免"编满一篇正确的废话"：

| 类别           | 判别                             | 处理                                                                                |
| -------------- | -------------------------------- | ----------------------------------------------------------------------------------- |
| **阻塞性缺口** | 缺了它这一节只能编               | **问用户**，最少 3 个，附"缺它会导致什么"；用户一时给不了就跳过该节、挂进待确认事项 |
| **可推导缺口** | 能从材料或公开信息推出           | 自己查（RAG / 检索 / 读参考文档），并标注推断依据                                   |
| **非阻塞缺口** | 不挡写现状与方案框架，只影响定稿 | 直接写不依赖它的内容；参数本身进待确认事项，不猜值、不写空话占位                    |

典型阻塞性缺口：文档类型与用途（给谁看、用于评审还是内部分工）、项目名称与建设范围、参考文档或既有材料、必须响应的要求（招标要求/任务书/上级批文）、时限与预算量级、以及会直接决定方案骨架的技术参数（规模量级、部署形态、必须对接的系统）。

**问不出来的，别写。** 用"业界通常做法是…"把评审风险转嫁给读者，是最容易被一眼看穿的写法；假设用"先用假设"顶过去也是同样的问题——用户看到的是具体数字时不会想到那是编的，而你也不知道自己编错了什么。真的推不出来又必须往下走的，写成 `［假设：…，待确认］` 并**在同一节说明不成立时的影响**，同时进待确认事项。

## 信息来源与工具调用

### 检索优先级

1. **用户材料**：参考文档、招标文件、任务书、历史方案、会议纪要。用户给了文件就读原文，不要凭记忆写。
2. **RAG 知识库（ragflow MCP，"手脚"）**：企业内部规范、历史项目文档、标准模板、术语口径都在这里。工具见下表。
3. **联网检索**：标准与法规（GB/T、行业规范）、政策与公开数据、竞品与同行方案、技术事实核对。
4. **问用户**：以上都给不出会改变正文写法的关键条件时，直接问或索取文档，不要含糊带过。

### 检索动作对照

| 需求                         | 动作                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------- |
| 不知道知识库里有什么         | `ragflow_list_datasets_tool` 列数据集，必要时 `ragflow_list_documents_tool` 看文档清单 |
| 按主题找依据                 | `ragflow_retrieval_tool`（`query` 用业务术语而非口语描述，`top_k` 5-10）               |
| 逐段读某个文档               | `ragflow_list_chunks_tool`，按页取 chunk                                               |
| 材料还没入库                 | `ragflow_upload_document_tool` + `ragflow_parse_document_sync_tool`                    |
| 公开信息、标准条款、政策数据 | `web_search` → `web_fetch` 取原文                                                      |
| PDF 里的表格与条款           | `mcp__pdf-reader__read_pdf` / `search_pdf`                                             |
| 已有 Word 稿                 | `mcp__docx__*` 读取与改写                                                              |
| 交付 Word                    | `mcp__docx__*`，或用项目脚本转换                                                       |

**ragflow 不可用时的降级**：`RAGFLOW_API_KEY` / `RAGFLOW_URL` 未配置会导致该 MCP 启动失败。此时改用 `pdf-reader`、`web_search` 加用户材料，**不要**假装检索过；在交付说明里写明"知识库未接入，以下内容基于公开资料与用户材料"。

**引用要落到可核对的锚点**：RAG 结果写来源文档名 + chunk 位置；网页写标题 + URL；用户材料写文件名 + 章节/页码。检索到的事实与用户材料冲突时，以用户材料为准，并把冲突写进交付说明。

## 写作流程

**铁律：禁止一口气写完整个文件。** 必须走「大纲 → 大纲里标引用 → 按照标的引用去看原文分章写正文」三步：先把大纲列到三级，再在大纲里标清每节要引用哪份文件的哪个章节，然后**照着标记去把原文调出来读**，读到什么写什么，分章成文。中间可以反复回头改大纲，直到大纲合理为止。跳过任何一步——尤其是跳过"回原文"这一步——产出的必然是正确的废话加编造引用。

### 阶段 A：研究

- 先读用户材料，抽出**术语表**（同一概念在全文中只用一个说法）和**事实清单**（数字、时间、接口、规模、约束）。
- RAG 检索 2-3 个不同角度（业务/技术/合规），把可用证据放进事实清单，标明来源。
- 联网补标准、政策、竞品与需核对的数字。
- 仍无法确认的事实：列入"待确认清单"，不写进正文结论。

### 阶段 B：出大纲（列到三级标题）

产出 `<文档名>.outline.md`，用 Markdown 标题表达层级：

- `#` 文档名（与最终交付文件同名）
- `##` 一级章（一、二、三…，与 `references/doc-structures.md` 的骨架、或招标/申报要求的章节逐条对齐）
- `###` 二级节（（一）（二）…）
- `####` 三级条（1. 2. 3.…）——**必须列到这一层才叫大纲**，只列到二级不算

结构对不齐要求时，先改大纲、不要硬写：章节顺序、增删、合并都在这一步解决。

### 阶段 C：在大纲里标引用（黄色标记）

**这一步是必须的，不能跳。** 每个三级标题（`####`）下面用黄色标记写清本节要引用哪份文件的哪个章节的哪些内容，用 `<mark>` 呈现，编辑器和预览里就是黄底：

```markdown
#### 1. 现状与现有系统清单

<mark>【引用】《XX 园区信息化现状调研报告》§2.1 现有系统台账（第 3 页）：门禁 1264 台读头、日均刷卡
记录 8 万条；停车 3 进 3 出共 6 条车道，日均 2100 车次。【摘抄】"现有门禁系统由 A 厂商 2019 年建设，
未提供对外数据接口"。</mark>
<mark>【检索】GB/T 22239—2019 等保三级身份鉴别条款（来源：《信息安全技术 网络安全等级保护基本要求》）</mark>
<mark>【RAG】知识库《园区数据治理规范 v2》，chunk 12：设备编码规则为"园区码-楼栋-设备类型-序号"。</mark>
<mark>【假设】停车系统接口为 HTTP 推送，待用户或厂商确认；不成立时改 JDBC 轮询。</mark>
```

规则：

- **每条三级标题至少一条 `<mark>`**；没有任何标记的条目，说明这节无依据，要么去检索补上，要么删掉该节。
- 标记必须写到**章节号 + 具体内容**（"§2.1 现有系统台账（第 3 页）"、"chunk 12"、"招标文件 3.2.1 条"），只写文件名不算。
- 标记的类型只有五种：`【引用】`（可能摘抄原话）、`【检索】`（联网查到的标准/政策/数据）、`【RAG】`（知识库命中）、`【假设】`（先用假设、待确认）、`【数据】`（本项目实测/现成的数字，注明出处）。
- **黄色标记里的内容必须是你真的读到过的**。没读到的写成 `【待补】` 并说明卡在哪（缺哪份文件、要用户给什么），不要编。
- 这一步顺手把全篇的术语表定下来，正文阶段不再改术语。

用 `node .dsh/skills/skills-doc-writer/scripts/outline-check.mjs <大纲.md>` 机械核对：有没有漏标的条目、标记是不是只写了文件名没写到章节、有没有留 `【待补】`。

### 阶段 D：按标记去看原文，分章写正文（loop：看原文 → 写 → 按需改大纲）

**写每一节之前，先照着这一节的 `<mark>` 标记把原文调出来读**，读完再写：

| 标记类型   | 动手写之前必须先做的动作                              | 标记转正式引用要记下的信息                            |
| ---------- | ----------------------------------------------------- | ----------------------------------------------------- |
| `【引用】` | 打开被引文件，定位到标记的章节/页码                   | 资料名称 + 章节/页码 + 采用内容（照抄哪句、改了哪处） |
| `【摘抄】` | 读到原话，逐字核对（连标点和数字一起核）              | 资料名称 + 章节/页码 + 原话全文                       |
| `【检索】` | `web_fetch` 打开来源页读出原文；标准要读到条款原文    | 标准号或标题 + 条款号 + 发布日期 + URL                |
| `【RAG】`  | 用 `ragflow_list_chunks_tool` 取到该 chunk 的原文内容 | 知识库文档名 + chunk 位置 + 命中内容                  |
| `【数据】` | 回到数据来源（测试报告、台账、统计表）核对数值与口径  | 数值 + 测量/统计时间 + 出处                           |
| `【假设】` | 无需读原文，但正文里要显式标注假设与退路              | 假设内容 + 退路 + 需要在什么节点前确认                |

**黄色标记只是查找索引，不是正式引用。** 每写完一节，把该节用到的标记就地升级成正式引用记录（上表第三列的四项信息），正文里按 `references/reference-writing.md` 的格式标注。用过 `<mark>` 却没留下这几项信息的，视为未完成。

读原文时发现与标记写的不一致（章节号记错、数字不符、原文语境不支持本节的论点）→ 先改标记、再写正文；发现这一节根本没有可引的材料 → 回改大纲，别硬写。

#### D1. 编写顺序：不要从第 1 章顺着写

顺着写的结果是：目标、原则、概述这类**总括性章节**先写，此时架构、功能、流程都还没定，只能堆概念——这正是"建设目标写成空话"的成因。改成先写约束力最强的章节，最后回头提炼总括章节：

1. **范围与职责划分**（约束后面所有设计）
2. **用户角色与业务运行**
3. **产品/数据对象体系**（术语和数据对象的定义源头）
4. **总体架构与组成**（各方后续引用的基准图）
5. **功能、流程、存储、接口**等实现性章节
6. **指标、保障、验收、风险**等收口章节
7. **最后回头写目标/原则/概述**，从已经成形的架构、功能、流程里提炼

正文编号不动，只调整实际编写顺序；回头写的章节要跟前面已定的架构、术语、数值对齐。用户给了编写顺序就按用户的，本条是默认值。

#### D2. 核心图表：只有文字必然空泛

长文档不能通篇是字。按文档类型先定**图表清单**（章节号 + 图名 + 要表达什么关系），写每章时同步出图或用文字+ASCII 占位，交付前清点：

| 文档类型            | 至少要有的图                                                                                                                                                               |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 技术方案 / 总体方案 | 外部关系图（本系统与外部系统/伙伴的边界）、业务流程图（端到端）、总体架构与组成图、数据/对象谱系图、任务与异常处理流程图、数据存储编目分发关系图、运维监控与质量控制关系图 |
| 需求/设计文档       | 用例或角色图、业务流程图、模块结构与依赖图、E-R 图、接口时序图、部署图                                                                                                     |
| 实施/验收文档       | 进度甘特或里程碑图、组织与责任矩阵、数据迁移流程图（含回退分支）、测试与验收流程图                                                                                         |
| 可研/建议书         | 建设内容框图、投资构成图、实施进度图、效益与指标对应关系表                                                                                                                 |

图的判定标准与文字一样：**能不能替代一段空话**。只画框不标关系、只有标题没有要素的图，等于没画。

#### D3. 参数未定：先问用户，问不到就留白，不许用空话占位

缺参数时的默认动作是**问用户**，不是自己想办法绕过去。

1. **先判断这个参数挡不挡得住写这一节**：
   - 挡住 → 这一节先不写正文，把问题问用户（一次最多 3 个，附上"缺它会导致什么"，让用户知道优先级）；用户一时给不了，就挂进待确认事项，正文对应位置留引路句，跳过这一节继续写别的。
   - 只影响定稿、不挡写现状与方案框架 → 直接写那些不依赖它的内容，参数本身进待确认事项。
2. **不许写的三类东西**（都比留白更糟）：
   - 推测数值（"日均约 2TB"这类没有来源的数字）——评审一问就崩；
   - 用"能力/流程/参数项/测算方法"重新包装一遍的空话——换个说法仍然是废话，判据见 `references/anti-slop.md`；
   - "待定""视情况""按甲方要求"这类空白响应。
3. **允许保留的只有两种**：一是有来源的事实（现状数据、既有系统情况、已确认的约束），二是**已经在执行的约定的引路句**——点明该参数属于哪一类参数、由谁提供、最迟何时确认、在哪一节表格里出现，例如"单星数据量与峰值下传速率取值见第 15 章待确认事项第 2 项"。引路句只在参数已经进入待确认表、且有责任方和确认节点时才写；没有这两项，就说明这个参数还没问出去，先把问题问了。

写完后自查一句：**这一节里有没有一句话是"因为没有数据，所以写得泛"的产物？** 有就删，改成提问或引路句。

#### D4. 待确认事项集中管理

写作过程中会不断冒出"待确认"。**不要散落在各章节**（正文里到处"待定"直接扣评审分），统一汇总到文末的「待确认事项」章节（独立一章，编号按文档结构定），每项至少五列：

| 序号 | 待确认内容                         | 影响章节     | 责任方       | 需取得的资料           | 最迟确认节点 |
| ---- | ---------------------------------- | ------------ | ------------ | ---------------------- | ------------ |
| 1    | 产品等级划分与命名规则的正式评审版 | §5、§10      | 甲方业务部门 | 评审通过的等级定义文件 | 详设启动前   |
| 2    | 单星数据量与峰值下传速率           | §11 指标测算 | 载荷方       | 载荷参数表             | 定稿前       |

正文里对应位置只写到引路句（"取值见第 X 章待确认事项第 N 项"），不写"待定"，也不替用户编一个值。

**待确认事项每增加一项，就同步检查一次：这一项是不是该直接问用户？** 能问的当场问掉，问不动的（要等外部厂商、等上级批文）才留在表里。

正文**按章节逐段写，一次一章或一节，不要一次生成整篇**。每写完一章：

1. 对着大纲核对该章的引用是否都用上、标记是否都已升级成正式引用、有没有临时新加的、有没有该引而没引的；
2. 写的过程中发现大纲不合理（拆章、并章、调顺序、某节其实没内容、某节证据不足写不出来）→ **回头改大纲**，同步改黄色标记，再继续写；
3. 改完大纲后，已写的章节如果受影响，一并回改，保持正文与大纲一致。

这个 loop 一直走到大纲稳定：连续写 2-3 章都没再动大纲，才算大纲合理。

写作细则：每段按"**主张 → 依据 → 边界/取舍**"写；表格承载对比信息（现状/目标、方案 A/B、招采条款响应），正文承载因果与取舍；有参考文档时按 `references/reference-writing.md` 仿写或摘抄。

### 阶段 E：自检（交付前必做）

1. 按 `references/checklist.md` 逐条过。
2. 跑确定性扫描：`node .dsh/skills/skills-doc-writer/scripts/doc-lint.mjs <草稿.md>`。脚本只报确定性问题（禁用词、长句、段落雷同、总结句、标点习惯），判断仍由你来做。
3. 逐段问一句"这段删了会损失什么"；答不出来的删或改成有信息的句子。
4. 核对每个数字、每个引用的来源是否写清；核对承诺性表述是否有依据。
5. 大纲里的 `<mark>` 标记写的是**引用来源**，正文交付前统一收进"来源与引用清单"，正文里按 `references/reference-writing.md` 的格式标注（引号 + 文件名 + 章节号），不要直接把黄底标记留在成稿正文里。

## 输出契约

- **长文档（>3000 字）默认三步交付**：先给三级大纲文件（含黄色引用标记）→ 按标记读原文、分章给正文。大纲交给用户看是为了**并行纠偏**，不是等确认才动手；用户没表态就按自己的判断继续写，把不确定项记进待确认事项。
- 正文**直接给完整文档**，不要只给提纲（除非用户明确只要提纲）。
- 交付时附四样（可短）：
  1. **来源与引用清单**：哪一段用了哪份材料的原话或数据，按阶段 D 表格的四项信息记录（资料名称、章节/页码、采用内容、URL 或出处）；
  2. **待确认事项**：长文档集中成文末独立章节（含影响章节、责任方、需取得的资料、最迟确认节点）；短文档在交付说明里列成同样结构的表；
  3. **图表清单**：每张图的编号、图名、所在章节、要表达的关系；还没出图的标注"待出图"，不要用空格或占位图糊过去；
  4. **未覆盖项**：用户要求但材料不足、没写的部分，直说没写。
- 长文档落成文件（默认 `docs/`，Markdown；需要交付 Word 时用 docx MCP 生成）；短文档（≤3000 字）可直接在对话中给出，但同样先过大纲、先标引用、按标记读过原文再写。
- **不要为了"准备更充分"而反复索取资料，也不要因为缺参数就写空话**：区分"阻塞编写的条件"和"影响定稿的输入"。前者**当场问用户**（这是唯一该停下来问的情况），问不到就跳过那一节、挂进待确认事项；后者直接写不依赖它的内容，参数进待确认事项。缺参数 **不许** 用推测数值、空话或"待定"占位，只允许写有来源的事实，或已在待确认表里有责任方与确认节点的引路句。

## 硬性文风约束（正文必须满足）

1. **先大纲、先标引用、再按标记读原文分章写**：禁止一口气写完整个文件。顺序是「大纲 → 大纲里标引用 → 按照标的引用去看原文分章写正文」：三级大纲（`##`~`####`）→ 每条三级标题下用 `<mark>` 黄底标出引用来源（章节号 + 具体内容）→ **写每节前先按标记把原文调出来读**，读到什么写什么，分章成文；大纲不合理就改大纲再写，loop 到连续 2-3 章不必再改大纲为止。工具：`scripts/outline-check.mjs` 校验大纲，`scripts/doc-lint.mjs` 校验正文。
2. **禁止正确的废话**：任何行业都能套用、去掉不损失信息的句子一律不写。判据与对照示例见 `references/anti-slop.md`。
3. **有参考文档时优先仿写或摘抄**：20 字以上的完整表述直接引号摘抄并标来源；句式和术语跟参考文档保持一致。规则与边界见 `references/reference-writing.md`。
4. **不用一眼 AI 的词**：禁用词表见 `references/anti-slop.md` §2。宁可写得平实，不要写得"高级"。
5. **克制 AI 的句式与分词习惯**：句长要长短交错，不要每段等长、不要每段结尾都来一句总结、不要机械地"首先/其次/最后"，不要为了对齐凑三句排比。见 `references/anti-slop.md` §3、§4。
6. **术语与措辞全文一致**：同一事物不换名字，段落标题不换格式，不复述同一观点。
7. **不确定就说不确定**：用"在 XX 条件下"、"按 XX 口径"给出边界，不用"完全满足"、"零风险"、"国内领先"这类无依据的绝对表述。
8. **引用不得编造**：标准编号、文件名、URL、数据来源一律核实过才写；核实不到就写进待确认清单，不在正文里充当依据。编造引用是 AI 文档最严重的硬伤。
9. **每篇必须带上本项目专有事实**：全篇至少 10 处专有名词、数字、日期、系统名或场地信息（每 300 字约 1 处）。没有这些，方案证明不了读过招标文件与现场情况，这一条不做例外。
10. **核心图表不能缺**：长文档按 `references/doc-structures.md` §8 的清单先定要出哪些图，写到对应章节时同步出图（或用图表占位说明），交付前清点。通篇只有文字必然空泛。
11. **参数未定先问用户，不许填空**：缺参数时先把问题问出去（一次最多 3 个），问不到就跳过那一节、把参数挂进待确认事项；正文里不写推测数值、不写"待定"、也不许用"能力/流程/测算方法"包装成空话占位（见阶段 D3）。
12. **待确认事项集中一处**：正文不散落"待定"，长文档统一汇总到文末独立章节（内容、影响章节、责任方、需取得的资料、最迟确认节点），正文对应位置回指该章节。

## 资源文档

- `references/anti-slop.md` — 废话判据与改写对照、AI 禁用词表、句式与段落节奏硬指标、量化指标表、规则来源可靠性分级。**写作和自检时必读。**
- `references/reference-writing.md` — 仿写/摘抄规则：术语表与事实清单、什么时候直接引原话、什么时候改写、引用标注格式、不得编造引用；附录给出大纲黄色标记的完整写法。
- `references/doc-structures.md` — 技术方案、项目建议书、可研报告、投标技术方案、实施/运维/验收文档的章节骨架与必备要素，含公文体例与数字用法、评审扣分与废标风险。
- `references/checklist.md` — 交付前检查清单（内容与依据、文风与 AI 痕迹、体例格式、评审风险四组）。
- `scripts/outline-check.mjs` — 大纲校验脚本：检查三级标题是否漏标引用、标记是否写到章节号、是否还有 `【待补】`。
- `scripts/doc-lint.mjs` — 正文确定性文风扫描脚本（零依赖 Node，Windows/Linux 均可跑）。

```bash
# 1) 先校验大纲；退出码 1 表示有三级标题没标引用来源
node .dsh/skills/skills-doc-writer/scripts/outline-check.mjs docs/技术方案.outline.md
# 2) 分章写完正文后再扫正文；退出码 1 表示有严重项
node .dsh/skills/skills-doc-writer/scripts/doc-lint.mjs docs/技术方案.md
# 正文里引用原文、规则表之类"本来就要写这些词"的位置，用行内指令跳过该行
#   <!-- doc-lint-ignore -->      单行忽略
#   <!-- doc-lint-disable --> / <!-- doc-lint-enable -->   区间忽略
```
