# 去 AI 腔规则集

<!-- doc-lint-rules-only -->
<!-- 本文件本身是规则表，通篇都是禁用词与反例：整篇跳过 doc-lint.mjs 的词表检查，保留节奏、残留、结构检查。 -->

写作时按本文件写，交付前按本文件查。规则分五层：先杀掉废话，再换掉词，再改句式，再调节奏，最后管住引用。

**硬性量化指标**（交付前逐条核对，用 `scripts/doc-lint.mjs` 扫）：

| 指标 | 要求 |
| --- | --- |
| 破折号「——」 | 全文 ≤1 处/千字（一页 800 字最多 1 个），单行不得出现 2 处 |
| 加粗 | 每章 ≤1 处，全文 ≤5 处；「**名词**：解释」式内联列表改写成散句 |
| 感叹号、emoji | 正式方案正文 0 个 |
| 句长 | 30 字以上的句子与 5-15 字的短句比例不低于 4:1；连续 3 句长度相近必须打断 |
| 段落 | 至少一段只有一句；至少一节明显比其他节短；不要所有段落都是 3-4 行 |
| 具体事实密度 | 每 300 字至少出现 1 个专有名词、数字或日期 |
| 「不是……而是……」 | 全文 ≤2 次，超出改为正面陈述 |

## 1. 正确的废话：判据与改写

### 五条判据（满足任一条即判废话，两条以上必删）

1. **删除测试**：把这句删掉，读者对项目、方案、取舍的理解是否变化？不变 → 废话。
2. **换主语测试**：把句中的项目/公司/系统名换成任意同类对象，句子照样成立 → 废话。
3. **要素测试**：句中没有任何专有名词、数字、时间、接口名、约束条件、因果关系、取舍理由 → 要么补证据，要么删。
4. **可执行性测试**：读完后无法据此做出任何决定，也核对不出任何事实。
5. **「所以呢」测试**：读完问一句"所以呢"，答不上来。

一段话必须至少推进一个事实。一段里全是"重要、关键、有力支撑"，这段就没有存在价值。

### 废话 → 有信息量：改写对照

| 正确的废话 | 有信息量的写法 |
| --- | --- |
| 本项目采用先进的技术架构，确保系统的高可用性与可扩展性。 | 服务按无状态设计，两个实例挂 Nginx 轮询；会话数据放 Redis，任一实例宕机后 30 秒内由健康检查摘除，用户重新登录即可，不做会话保持。 |
| 通过数据治理提升数据质量，为决策提供有力支撑。 | 治理范围是车辆台账和人员台账两张表：统一车牌与工号的编码格式，补齐缺失的责任部门字段（现状约 1.2 万行缺失），完成后两张表可按人/车关联查询。 |
| 加强安全管理，保障系统稳定运行。 | 数据库账号按读写分离授权，应用只有 DML 权限；备份每日 02:00 全量、每小时增量，保留 30 天，恢复到验证环境的实测耗时 22 分钟。 |
| 系统具有良好的扩展性，可满足未来业务发展需要。 | 新增一类设备接入的改动点是三处：设备类型字典加一条记录、解析器目录加一个模块、前端加一个展示组件；不改动数据汇聚主流程。 |
| 根据项目实际情况，合理安排实施进度。 | 工期 90 天，前 20 天做接口联调（依赖门禁厂商提供接口文档），第 21 天起进入开发；若接口文档延迟一周，整体顺延一周。 |
| 将有效降低运维成本，提升管理效率。 | 现状是 3 个人各管一套系统的报表，每周花约 6 小时手工汇总；平台上线后周报由定时任务生成，人工核对时间降到约 30 分钟。 |
| 充分考虑各类风险，制定相应的应对措施。 | 主要风险是门禁厂商接口不开放：若 7 月 15 日前拿不到接口文档，改走数据库只读账号轮询方案，采集延迟从 5 分钟放宽到 15 分钟，成本增加 3 人日。 |
| 高度重视数据安全，采取多重防护手段。 | 个人信息字段（姓名、手机号、身份证号）在库内用 AES-256 加密存储，密钥由甲方 KMS 托管；查询接口只返回脱敏值，导出功能需二级审批。 |
| 本项目将有力推动园区数字化转型升级。 | 删掉。这句话不影响任何人对方案的理解，保留只会稀释前面的具体内容。 |

### 常见废话句式（见到就改或删）

- 「为……提供有力支撑 / 保障 / 支撑作用」
- 「具有重要的现实意义 / 深远意义 / 广阔的应用前景」
- 「有利于提升……，有利于降低……」（没有量化就不叫论据）
- 「不仅能……，还能……」开头接空泛收益
- 「综上所述」后面重复前文
- 「随着……的不断深入」
- 用「进一步提升、不断完善、持续推进」收尾（没有对象和指标的"进一步"是空话）

## 2. 禁用词表

### 2.1 绝对不用（见到即改）

**大帽子开头**：在当今……、随着科技的飞速发展、随着时代的进步、在……的大背景下

**报告体收束**：综上所述、总而言之、总的来说、一言以蔽之、由此可见、不难看出、众所周知、显而易见、值得注意的是、值得一提的是、需要注意的是、需要指出的是

**空转评价**：不容忽视、起着至关重要的作用、扮演着重要角色、起到了关键作用、具有重要的意义、广阔的应用前景

**一眼 AI 的商务热词**：赋能、闭环、抓手、护航、纵深推进、生态体系、护城河、底层逻辑、高质量发展、提质增效、降本增效、数字化转型、新引擎、注入新动能、新篇章、新高度、组合拳、打法、范式

**无依据的强度副词**：全方位、立体化、多维度、深层次、极大地、全面提升、有效提升、显著提升

**虚假归因**：业界普遍认为、业内普遍认为、有人说、据我观察、大家都知道、专家指出（不具名）——要么具名引用到人和出处，要么删掉归因只留事实。

**四字词堆砌**：行稳致远、未来可期、相辅相成、应运而生、与时俱进、意义深远、任重道远——同一段出现 2 个以上，这篇基本就是 AI 写的。

**引言腔**：本文将从……、接下来我们将……、让我们……

### 2.2 有条件可用

这些词本身没错，但 AI 爱用，用之前问自己三个问题：有没有更具体的说法？删掉会不会损失信息？作者会这么说吗？

| 词 | 用它的条件 |
| --- | --- |
| 赋能 | 建议改写成具体能力，例如"把评分模型开放给第三方调用" |
| 助力、致力于、旨在 | 换成具体动作动词："本期新增……"、"目标是……"（或直接陈述做法） |
| 深度融合、有机结合 | 指明融合的是哪两件事、融合后多出什么能力 |
| 有效提升、显著降低 | 后面必须要跟可核对的数字或口径 |
| 系统性、体系化、常态化、机制化 | 说明由哪几项制度/组件构成 |
| 有力地、切实、扎实 | 删掉，直接写做了什么 |
| 洞察、深谙、重塑、颠覆 | 给出事实依据（数据、案例、时间点），否则删 |
| 一体化、平台化 | 指明合并了哪几个原本独立的环节 |

### 2.3 翻译腔与抽象名词骨架

- **抽象名词 + 进行/作出/予以**：把「对数据进行清洗」写回「清洗数据」；「进行了三个方面的优化」→「优化了三处：……」
- **抽象名词当主语**：「系统的建设实现了……的管理」→ 写清谁做了什么：「运维人员现在能在同一张表里查人和车的进出记录」。
- **「是一个……的过程」**：删掉框架，直接写过程和结果。
- **英文直译**：「赋能于」→ 交给/开放给；「基于……的考虑」→ 因为；「在……方面」→ 直接说；「造成了……的影响」→ 影响了什么。
- **「进一步」「持续」「不断」单独修饰动作**：补上具体对象和数量，补不上就删。

## 3. 句式规则

1. **句长要长短交错**：以 20-45 字为主，允许 8-12 字的短句穿插，超过 80 字的句子拆开。全部句子都在 40 字左右，读起来就是机器写的。
2. **不强行对仗/排比**：不要为了凑"三个"而写三项。列表内容不足三项，就写两项。同句式连续出现 4 次以上必须改——判据是任意两项互换位置后读感不变。
3. **不机械使用「首先/其次/最后」**：正式方案的层级用「一、（一）1.」；逻辑上是并列或递进，就直说内容。
4. **不写口语插入语**：「总的来说」「不得不说」「需要说明的是」在方案里一律去掉；但**允许并鼓励**写清口径的话，如「按甲方提供的口径」「口径以 2024 年报为准」。
5. **不用「不是……而是……」句式**：全文最多 2 次。这是判断句，用在主观文案里可以，方案里改成事实陈述或取舍说明。
6. **不写虚假让步**：「当然，这些都很重要」「诚然……但是」这类三段式让步，全文最多 1 次；删掉让步句如果上下文依然通顺，说明它是装饰。
7. **不写立场真空**：「各有优缺点」「因人而异」「取决于多种因素」——要么给出判断，要么给出具体条件（"并发 500 以下用 A，跨机房用 B"）。给不出就删句。
8. **不写自赏句和假金句**：「差一个字，背后的系统设计完全不同」「X 不是工具，而是镜子」——还原成具体主张，还原不出来就删。
9. **标题不玩梗、不加 emoji、不剧透结论**：正式文档标题用名词短语，"调用链变了，信任模型也得跟着变"这种标题改成交代范围的写法（如"§4.3 信任模型调整"）。
10. **每段结尾不做总结**：段落末尾不要再把本段复述一遍。段首已经说了结论，结尾就直接进入信息或停住。
11. **段落开头方式不要一致**：连着好几段都用「通过……」「为……」「本项目……」开头，读起来像模板填空。
12. **允许不收尾**：删掉最后一段"综上所述"之后，不必补一个新的结尾段——直接停在最后一个具体句子上。
13. **段落之间不要求过渡句**：随机删掉一处过渡句，读者仍然跟得上，那么原过渡句是"安全垫"，删。

## 4. 克制 AI 的等长分段与分词习惯

AI 的默认输出习惯是**均匀**：段落等长、句子等长、每段一个论点加一句总结、术语反复换说法。真实的方案文档是**不匀**的——有的段落就两行，有的段落七八行；有的一张表接着说，有的需要连续论证。

具体要求：

1. **段落长度不求齐**：短段落可以只有一句（例如一条硬性约束），长段落可以写七八句（例如方案取舍论证）。不要把所有段落修剪成同样的三到四行。
2. **同一概念全文一个词**：技术术语、系统名、角色名定下来就不要换（别一会儿"管理平台"一会儿"管控系统"）。换词会让读者以为是两个东西，也让文本像改写拼接的。
3. **不复述**：同一个观点只讲一次。前一节讲过的技术选型，后一节引用一句"选型见 §3.2"即可，不要重讲一遍。
4. **少用并列列表替代论证**：列表适合罗列可枚举项（设备清单、接口参数、验收指标）。因果、权衡、边界这类内容用段落写，列表承载不了「为什么」。
5. **表格只放对比类信息**：现状/目标、方案 A/B、招标条款响应、职责分工。表格里不要写整句的形容词。
6. **章节标题格式保持一致，但内容详略按实需分配**：重要的章节写透，次要的章节可以两三句带过；不要为了篇幅均衡给每个小节都凑够同样的字数。
7. **不要在段末追加"金句"**：AI 习惯在段落结尾来一句格言式总结。删掉。
8. **不凑篇幅**：每节都要能回答"这一节给读者增加了哪一条读别的节得不到的信息"。答不出来的节删掉或并入他节，不要为了让章节看起来均衡而扩写。同理，不要写"复述上一章的结论"这种开场，也不要为了完整而重复已定论的内容——**完整性不靠篇幅，靠每条信息都有出处**。

## 6. 不要去刷 AI 检测率

这条要说清楚，避免走偏。

- **AIGC 检测分数不可靠**：不同平台（维普、万方、GPTZero 等）对同一篇文章的判定差距可达 30 个百分点以上，误判常见——学生自己写的计划书被判 97% AI 率、《荷塘月色》被判高 AIGC 率这类案例公开报道过。把某个分数当交付门槛，是在优化一个不稳定指标。
- **检测厂商的算法不公开且会变**：早期基于困惑度（perplexity）与突发性（burstiness）的说明已属旧口径，现在多为模型判别。（我未能核实具体厂商的最新说明——该说明页禁止自动抓取，此处只作方向性判断。）
- **为过检测而破坏文档质量是错的**：故意加语病、删连接词、堆砌生僻词，会让方案读起来像事故现场，评审照样扣分。
- **正确的目标**：写得**可读、有信息、来源可查**。真正让人相信这是一份认真写的方案的，是具体的数字、真实的取舍和能核对的引用，而不是降低某个检测分数。

刻意提升"像人"的程度，只做一件事：**把抽象表述换成具体事实**（写"临港机房 3 号柜的 42U"，而不是"数据中心基础设施"）。这一条既降 AI 痕迹，也提高文档质量。

## 7. 规则来源与可靠性分级

本文件与 `reference-writing.md` 的规则，来源可靠度不一致，按下列分级理解：

| 级别 | 内容 | 来源 |
| --- | --- | --- |
| **实践共识（可执行）** | 废话判据、句长/段落节奏、禁用词、引用标注、术语一致 | 通行中文写作与公文惯例；另参考两份公开的中文「去 AI 味」规则集（<https://raw.githubusercontent.com/Raymondhou0917/speak-human-tw/master/references/patterns.md>、<https://raw.githubusercontent.com/zero-click/avoid-ai-writing-zh/main/SKILL.md>），二者均为社区整理，非权威标准 |
| **规范依据（可判定）** | 公文体例、数字用法、评标响应要求 | GB/T 9704—2012、GB/T 15835—2011、《招标投标法实施条例》等，见 `doc-structures.md` §6、§7 |
| **证据较弱（参考即可）** | 破折号密度的具体数值、"多家投标方同源模板会被处罚"、"连续 N 字相同即判抄袭" | 未能核实到权威原文。本文件里的破折号阈值按经验取 ≤1 处/千字，宁严不宽；后两条不作为规则引用 |

写作时按规则执行，不必纠结来源；但如果要在正式材料里引用某个"研究表明"，先核实原始出处，核实不到就不引用——**编造引用是 AI 生成文档最严重的硬伤，比文风问题严重得多**。每条引用的出处要么查得到，要么写进待确认事项问用户；**不要用"估算"当挡箭牌**，无来源的数字标成估算仍然是编的。
