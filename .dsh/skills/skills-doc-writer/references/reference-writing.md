# 参考文档的仿写与摘抄规则

<!-- doc-lint-rules-only -->
<!-- 本文件是写作规则文档：整篇跳过 doc-lint.mjs 的词表检查，保留节奏、残留、结构检查。 -->

有参考文档时，**优先跟参考文档写**：术语、句式、口径、详略都跟着走。这不是偷懒，是让文档与本单位的既有材料保持一致，也最不容易露出 AI 痕迹。

---

## 0. 先建两张表（读材料的产出物）

读完材料再动笔，先出这两张表（可以放草稿区，不必进正文）：

**术语表**：固定全篇用词，避免同一事物换名字。

| 概念 | 参考文档用词（采用） | 禁止的替代写法 |
| --- | --- | --- |
| 监管对象 | 在建工程 | 施工现场、工地、项目现场 |
| 数据汇聚节点 | 数据中台 | 数据底座、数据平台、数据枢纽 |
| 责任角色 | 项目负责人 | 项目经理、项目主管 |

**事实清单**：每条带来源，正文里凡涉及这些事实，直接取用而不是自己编。

| 事实 | 数值/表述 | 来源（文件+位置） |
| --- | --- | --- |
| 现有设备接入数量 | 1264 台 | 项目现状说明 §2.1，第 3 页 |
| 采集频次要求 | 5 分钟 | 招标文件 3.2.1 条 |
| 工期 | 90 日历天 | 任务书第一条 |

## 1. 什么时候直接摘抄原话

满足以下任一条件，**用引号原样摘抄并标注来源**，不要改写：

1. **法规、标准、招标文件条款**：一字之差可能改变含义或导致废标。例：
   > 招标文件第三章 3.2.1 要求"系统应支持不少于 2000 个并发用户在线操作，平均响应时间不大于 2 秒"，本方案按 2400 并发、1.8 秒设计。
2. **技术规范、接口定义、参数口径**：指标值、单位、取值范围照抄，避免转述失真。
3. **内部文件的固定表述**：本单位既有的项目名称、系统名称、职责表述、审批流程表述。
4. **20 字以上、表达完整、无法更简的独立表述**：例如现状描述的完整句子、上级文件的要求段落。
5. **带数字或时间口径的句子**：改写容易把口径改掉。

**20 字以下的定型短语**（如「等保三级」「双活容灾」「雪亮工程」）：视为术语直接沿用，不必标注，但全文口径要统一。

摘抄长度控制：单处不超过 3 行；全文摘抄占比控制在 10% 以内，其余部分写自己的分析、方案和取舍。摘抄堆砌的文档反而更容易被看穿。

**句式可借，实体必须换**：参考文档的句式骨架和论述顺序可以照用（这正是"像本行业的人写的"的主要来源），但数字、型号、规模、时间、单位名称必须换成本文档的真实值。

## 2. 什么时候改写

以下情况要改写，不是照抄：

- 原文是口语、会议纪要、聊天记录 → 转写成规范书面语；
- 原文与本文档的详略层次不匹配（原文一段讲完的事，本文要展开成小节；或原文整章内容本文只需一句）；
- 原文存在前后矛盾、口径过时、术语不统一 → 先向用户确认取哪个口径，再统一改写；
- 原文属于他人著作权材料（第三方白皮书、厂商宣传页）→ 只能转述并标明出处，不整段摘抄。

**改写的边界：只动句式，不动事实。**

允许改：句子结构、语序、连接方式、详略展开、从叙述改为表格。

禁止改：术语、数值、单位、时间、范围、条件、因果方向、责任主体。改完之后若与原意有出入，回退原句直接引用。

一处拿不准原文含义时，标 `［待确认：原文"XX"的准确口径］` 交给用户，不要猜。

## 3. 引用标注格式

| 来源类型 | 标注写法 |
| --- | --- |
| 用户提供的文档 | 引号摘抄后紧跟 `（来源：《文件名》§章节名）`；关键条款写条款号 |
| RAG 知识库检索结果 | `（来源：知识库《文档名》，chunk 位置/章节）` |
| 网页、标准、政策 | `（来源：《标题》，发布日期，URL）` |
| 用户口述 | `（来源：用户提供，YYYY-MM-DD 沟通）` |

正文中不做脚注堆砌时，用交付说明里的**来源与引用清单**统一列出：哪一段用了哪份材料的原话。

引用冲突处理：用户材料与检索结果不一致 → 以用户材料为准，并在交付说明中写明冲突点与取舍理由。

## 4. 一致性要求

- **术语全文唯一**：参考文档叫「数据中台」，全文就只叫「数据中台」。
- **口径全文唯一**：同一指标不在不同章节用不同数值或用不同统计口径。
- **称谓统一**：投标类文档对采购方统一「采购人/贵方」，自称「投标人/我方」；建设类文档统一「建设单位/承建单位」。不混用「我们」「本公司」「甲方爸爸」这类口语。
- **详略跟随文档用途**：给评审看的把依据写足，给施工看的把步骤写细；同一份文档里同类章节的详略要一致。

## 5. 引用不得编造（最高优先级）

编造引用是 AI 生成文档最严重的硬伤，比文风问题严重得多——评审一旦抽查到不存在的文件，整份方案的可信度归零。

- **标准、法规、政策**：必须写出准确编号与名称（如「GB/T 15835—2011《出版物上数字用法》」「发改投资规〔2023〕304 号」）。写之前核实过才写；没核实过就只写做法、不引编号。
- **文献、报告、数据**：写出来源名称、发布机构、时间、URL，且这些必须来自实际检索到的页面。**禁止凭印象写"据某研究""业内报告显示""据权威机构统计"。**
- **不具名归因一律删**：「业界普遍认为」「专家指出」「有资料显示」——要么补上具名出处，要么删掉归因只保留事实本身。
- **核实不到的**：标注 `［未经核实：来源待补］` 写进交付说明的待确认清单，不留在正文里充当依据。

## 6. 大纲阶段的黄色标记（写正文之前必须做完）

正文不要一口气写完。第一步出三级大纲，第二步在大纲里用黄色标记写清"这一节要用哪份文件的哪个章节的哪些内容"，第三步**按标记把原文调出来读，读到什么写什么**，分章成文。黄色标记是引用规则从"读完记在脑子里"变成"写下来能核对"的关键一步——没有它，正文阶段的引用全靠回忆，编造就是这么发生的；有了标记却不回原文，等于只多了一层形式。

### 6.1 呈现方式

用 HTML `<mark>` 标签，Markdown 编辑器、VS Code 预览、Typora 里都是黄底高亮，且不依赖特定编辑器主题：

```markdown
#### 2. 现有系统清单

<mark>【引用】《XX 园区信息化现状调研报告》§2.1 现有系统台账（第 3 页）：门禁 1264 台读头、日均刷卡记录
8 万条；停车 3 进 3 出共 6 条车道、日均 2100 车次。</mark>
<mark>【摘抄】同上 §2.1 原文："现有门禁系统由 A 厂商 2019 年建设，未提供对外数据接口"。</mark>
<mark>【检索】GB/T 22239—2019 等保三级身份鉴别条款（来源：《信息安全技术 网络安全等级保护基本要求》）。</mark>
<mark>【RAG】知识库《园区数据治理规范 v2》chunk 12：设备编码规则"园区码-楼栋-设备类型-序号"。</mark>
<mark>【数据】本项目实测：单机 PostgreSQL 16 在 120 万行/日增量下查询 P95 = 860ms（2026-08-20 测试环境）。</mark>
<mark>【假设】停车系统接口为 HTTP 推送，待确认；不成立时改 JDBC 轮询，工期 +2 人日。</mark>
```

### 6.2 标记类型（只用这六种）

| 前缀 | 用于 | 必须写到什么粒度 |
| --- | --- | --- |
| `【引用】` | 用户提供的文档 | 文件名 + 章节号/页码 + 本节要用到的具体内容 |
| `【摘抄】` | 打算原话照抄的句子 | 文件名 + 章节号 + 引号内的原话（≥20 字） |
| `【检索】` | 联网查到的标准、政策、数据 | 标准号或标题 + 条款/章节 + URL 或发布日期 |
| `【RAG】` | 知识库命中 | 知识库文档名 + chunk 位置 + 命中的具体内容 |
| `【数据】` | 本项目的实测值、现成统计 | 数值 + 测量时间 + 来源（谁测的、什么环境） |
| `【假设】` | 暂时按某条件推进 | 假设内容 + 不成立时的退路 |
| `【待补】` | 该节确实缺材料 | 缺什么、要向谁要（交正文前必须清零或转成待确认清单） |

### 6.3 硬规则

- 大纲必须列到三级（`####`）。每个三级标题下**至少一条** `<mark>`；一条都没有，说明这节没有依据——要么去检索补上，要么把这一节删掉。
- 标记必须写到**章节号 + 具体内容**。"《招标文件》"、"见前文"、"同上"这种不算，脚本会直接判错——因为写到这个粒度，正文阶段还是得回头翻文件，等于没标。
- 标记里的内容必须是你**真的读到过**的。凭印象写的、转述二手信息的，写 `【待补】` 并说明卡在哪。
- 顺手在这一步把术语表定下来（哪个词用哪个说法），正文阶段不再改术语。
- 引用冲突在标记阶段就暴露出来：同一件事两份材料数字不一致，就在标记里写明取哪个、为什么，别等正文写完再改。

### 6.4 校验

```bash
node .dsh/skills/skills-doc-writer/scripts/outline-check.mjs docs/技术方案.outline.md
```

脚本检查：有没有三级标题、每个三级标题是否至少一条标记、标记是否写到锚点（§/页码/条号/chunk/URL/标准号）、是否用了"同上/见前文"、还剩多少 `【待补】`。**它不检查引用是否真实存在**，那必须人核。

### 6.5 大纲 → 正文的衔接

- **写每一节之前，按这一节的标记把原文调出来读**：`【引用】`打开文件定位到章节页码、`【摘抄】`逐字核对原话（含数字标点）、`【检索】`用 `web_fetch` 打开来源页、`【RAG】`用 `ragflow_list_chunks_tool` 取该 chunk 原文、`【数据】`回原始数据源核数值与口径。读到什么写什么。
- 读原文时发现与标记不符（章节号记错、数字不符、原文语境不支持本节论点）→ 先改标记再写；发现本节没有可引材料 → 回改大纲，别硬写。
- 正文按章节写，一次一章或一节，写完对照大纲核对引用是否都用上、有没有临时新加的。
- 发现大纲不合理（拆章、并章、调顺序、某节其实没内容、某节证据不足写不出来）→ **回头改大纲并同步改黄色标记**，再继续写；改完要回改已写章节，保持正文与大纲一致。
- loop 到连续 2-3 章不必再动大纲，才算大纲合理。
- 交付的正文里**不保留** `<mark>` 标记：按 §3 的引用格式标注来源（引号 + 文件名 + 章节号），黄底标记收进交付说明的"来源与引用清单"。

## 7. 容易踩的坑

- **改头换面式改写**：把原文每句换个同义词，事实却改错了——比直接引用更糟。
- **术语漂移**：前半篇「感知设备」，后半篇「传感终端」，读者会以为是两类设备。
- **把厂商宣传语当事实**：厂商材料里的"业界第一""领先 30%"必须核实或删除，正文不出现无依据的绝对表述。
- **摘抄未标注**：给评审看的文档摘抄他人材料不标注来源，属于硬伤。
- **保密材料外流**：内部文件、含个人信息的材料只在本地使用，摘要时脱敏（姓名、手机号、身份证号、账号），不写入交付文档。
