# 文档结构骨架与必备要素

<!-- doc-lint-rules-only -->
<!-- 本文件是写作规则文档：整篇跳过 doc-lint.mjs 的词表检查，保留节奏、残留、结构检查。 -->

本文件给的是**骨架和必备要素**，不是填空模板。实际章节顺序以招标文件、申报通知、任务书或上级大纲的要求为准；有官方编写大纲时，逐条对齐它的章节，不自创顺序。

> 表头标注：〔规范〕= 有法规、国标或官方大纲条文支撑；〔惯例〕= 行业评审实践中的常见要求，合同中没写但评委照问。

---

## 0. 所有方案类文档都要有的东西（缺了必被问）

| 要素 | 要求 | 依据 |
| --- | --- | --- |
| 编制依据 | 列出法规、规划、标准规范的**具体名称和条款号**，不是只列文件名 | 〔惯例〕评审必查 |
| 现状与问题 | 具体到系统名、数据量、流程、耗时、责任人；不写"管理粗放"这种评价 | 〔规范〕需求分析前置条件 |
| 需求量化 | 至少覆盖四类指标：功能指标、信息量指标（数据量/并发/存储）、性能指标、软硬件配置清单 | 〔规范〕信息化项目设计编制要求 |
| 建设内容边界 | 明确做什么，**明确不做什么**（改造范围、不替换的存量系统） | 〔惯例〕防范围争议 |
| 方案比选 | 至少两个候选方案的技术/成本对比表 + 推荐理由（合理性、先进性、适用性、可靠性、安全性、经济性） | 〔规范〕可研与建设方案大纲 |
| 进度与人力 | 工期、分阶段里程碑、关键路径、人员配置（角色 + 人月 + 是否驻场） | 〔规范〕建设管理方案要求 |
| 投资概算 | 分项概算 + 精度声明（可研阶段要求 ±10% 以内）+ 编制口径 | 〔规范〕 |
| 风险与应急 | 风险、概率、影响、应对措施、责任人；覆盖需求/建设/运营/网络与数据安全 | 〔规范〕 |
| 验收标准 | 每项技术、服务、安全标准的判定方法与验收材料；指标要能被第三方复现测量 | 〔规范〕验收需第三方测评报告 |
| 假设与前提 | 显式列出并说明假设不成立时的退路 | 〔惯例〕评审提问高发点 |
| 遗留问题 | 未决事项、责任人、关闭时间、验证方式 | 〔惯例〕 |
| 效益指标 | 与验收指标一一对应，形成"指标—验收方法—验收材料"闭环 | 〔规范〕 |

## 1. 技术方案（信息化/智能化/工程类）

适用：企业内部技术方案、集成项目技术方案、系统建设方案。

```
一、项目概述
  （一）项目背景与依据
  （二）建设目标（可判定，不写"全面提升管理水平"）
  （三）建设范围与边界（含不做什么）
  （四）术语与缩略语
二、现状与需求分析
  （一）现状：现有系统清单、数据规模、流程耗时、既有问题（带数字）
  （二）业务需求：场景、角色、流程改造点
  （三）功能需求：功能指标清单（可逐条验收）
  （四）性能与容量需求：并发、响应时间、数据量、存储与增长
  （五）接口与集成需求：对接系统的接口方式、频次、数据归属
  （六）安全与合规需求：等保定级、个人信息处理、密码应用、数据共享属性
三、总体设计
  （一）设计原则与约束
  （二）总体架构（分层图 + 文字说明各层职责）
  （三）技术路线与选型（含比选表与取舍理由）
  （四）部署架构（网络分区、资源清单、软硬件配置清单）
四、详细设计
  （一）功能模块设计
  （二）数据设计：数据模型、编码规范、数据流、存储与保留策略
  （三）接口设计：接口清单（名称/方式/频次/字段/异常）
  （四）安全设计
五、实施计划
  （一）进度计划与里程碑
  （二）人力配置与职责
  （三）测试与试运行方案
六、投资概算
七、风险与应对
八、验收标准与交付物
附：设备与软件清单、接口清单、数据字典、图表索引
```

## 2. 项目建议书

```
一、项目概况（名称、承办单位、地点、期限、总投资与资金来源）
二、建设必要性（政策依据 + 现状问题 + 不建的后果）
三、需求分析与建设内容（功能/信息量/性能/配置四类指标）
四、建设方案（总体思路 + 主要建设内容 + 技术路线）
五、要素保障（资金、场地、网络、人员、数据来源）
六、进度安排
七、投资估算与资金筹措
八、效益分析（经济、社会、管理效益；能量化的量化，不能量化的写口径）
九、风险与对策
十、结论与建议
```

要点：建议书是"要不要干"的论证，重点在**必要性 + 建设内容边界 + 投资量级**，不追求详细设计深度。

## 3. 可行性研究报告

〔规范〕政府投资项目按《政府投资项目可行性研究报告编写通用大纲（2023 年版）》（发改投资规〔2023〕304 号）十一章编写：

```
一、概述（项目概况、编制依据、主要结论）
二、项目建设背景和必要性
三、项目需求分析与产出方案
四、项目选址与要素保障
五、项目建设方案
六、项目运营方案
七、项目投融资与财务方案
八、项目影响效果分析
九、项目风险管控方案
十、研究结论及建议
十一、附表、附图和附件
```

要点：
- 投资估算精度按可研阶段要求（±10% 以内），并写明估算口径与依据。
- 风险识别要覆盖需求、建设、运营、融资、财务、经济、社会、环境、网络与数据安全，并评价发生可能性与损失程度。
- 「需求或绩效目标不明确」「资源需求说不清」在评审中直接不予支持——需求分析章节必须给出量化目标。

## 4. 投标技术方案

投标文件的写法由招标文件决定，核心不是"写得好"，而是**逐条响应、可被评委核对**。

```
一、投标人基本情况与类似业绩
二、对项目的理解与需求响应
三、技术方案（结构参照 §1，章节标题与评分项措辞一致）
四、技术响应/偏离表  ← 必做
五、项目管理与实施组织（机构、关键岗位人员、投入人月）
六、进度计划与保障措施（含延期补救）
七、质量保证措施与可度量质量目标（缺陷密度、可用率等）
八、培训与售后服务（响应时限、到场时限、备件）
九、风险与应急预案
十、验收方案与验收标准
附：资质、业绩、人员证书、设备清单
```

**偏离表格式**：

| 招标文件条款号 | 招标要求 | 投标响应 | 偏离性质 | 响应值/证据位置 |
| --- | --- | --- | --- | --- |
| 第三章 3.2.1★ | 支持不少于 2000 并发用户 | 满足，实测 2400 并发，响应 1.8s | 无偏离 | 见 §3.4 性能测试报告 |
| 第三章 3.2.5▲ | 提供国产化数据库适配 | 支持达梦 DM8，已通过适配测试 | 正偏离 | 见附件 6 |

要点〔规范〕：
- 投标文件必须对招标文件的**实质性要求**逐条响应，未响应属于否决投标情形（《招标投标法实施条例》第五十一条）。
- 中标条件是满足全部实质性要求且量化指标得分最高；招标文件未规定的评标标准不得作为评审依据（《政府采购法实施条例》第三十四条）。
- 实质性指标出现负偏离一般直接否决；非实质性负偏离逐项扣分。
- 「★/▲」条款零负偏离，逐条给出量化证据；正偏离可加分，但要写清加分依据。
- 全文不得出现「待定」「视情况」「按甲方要求」式的空白响应。
- 称谓统一：对采购方用「采购人/贵方」，自称用「投标人/我方」，不混用「我们」「本公司」。

## 5. 实施方案 / 运维方案 / 验收方案

**实施方案**：实施组织与分工 → 详细进度（含关键路径与依赖）→ 环境与资源准备 → 数据迁移方案（含迁移范围、映射规则、校验方法与回退）→ 测试方案（单元/集成/性能/安全，含用例与通过标准）→ 上线与切换方案（含回退条件与决策人）→ 培训与文档交付 → 风险与应急。

**运维方案**：服务范围与边界 → 服务级别指标（可用率、响应时限、恢复时限 RTO、数据恢复点 RPO）→ 人员与值班安排 → 巡检与变更流程 → 事件分级与处置流程 → 备份与灾备（频率、保留期、恢复演练频次与实测耗时）→ 安全与保密要求 → 服务考核与结算方式。

**验收方案**：验收依据（合同条款号 + 招标文件条款号）→ 验收范围与分解（功能项逐条、性能指标逐项）→ 每项的验收方法与判定标准（含测量工具、样本量、通过阈值）→ 第三方测评安排 → 试运行期要求 → 验收材料清单 → 不通过的处理流程。

要点：验收指标必须**可被第三方复现测量**——写清测量环境、工具、样本与判定阈值，不写"运行稳定""用户满意"。

## 6. 常见评审扣分与废标风险（自查用）

〔规范〕法定后果类：

- [ ] 投标文件未按招标文件要求签字盖章（否决投标）
- [ ] 未对实质性要求作出响应（否决投标）
- [ ] 出现两个以上不同报价或方案（否决投标）
- [ ] 报价高于最高限价或低于成本（否决投标）
- [ ] 引用招标文件未规定的标准作为自评加分依据

〔惯例〕评审扣分类：

- [ ] 评分项用「方案全面/较全面」这类无客观标准的表述
- [ ] 技术参数未逐条响应、未标注偏离性质
- [ ] 需求与方案不对应（需求列了 20 条，方案只覆盖 12 条）
- [ ] 缺进度计划、人力配置、验收标准、风险应急
- [ ] 全文数字不自洽（概算表与正文、人力表与进度表对不上）
- [ ] 用「国内领先」「高性能」等不可核验表述替代具体指标
- [ ] 无来源数据未标注为估算

## 7. 公文体例与数字用法〔规范〕

- **层次序数**：一级「一、」二级「（一）」三级「1.」四级「（1）」。一级用顿号，三级用下脚点且其后不加空格，二、四级用中文全括号。常见错误写法：`一.`、`1、`、`（1）.`、半角括号 `(一)`。
- **数字用法**（GB/T 15835—2011）：计量、统计与编号用阿拉伯数字；概数用汉字（「三四个月」「五六十年前」），两位数字连用表示概数时中间**不加顿号**；同一场合同类别同形式，不混用「二〇二五年」与「2025 年」；年份不简写（写 1990 年，不写 90 年）；纯小数写出定位 0；数值范围用「~」或「—」且单位完整（写 15%~30%，不写 15~30%）。
- **标题**：单独成行的标题结尾不加句号、不加冒号；附件名称后不加标点、不加书名号。
- **不可核验表述禁用**：大概、基本上、尽量、差不多、业界领先、国内一流——要么给指标，要么标注为估算并说明依据。
- **不写无主体的空转句**：如「相关部门应加强管理」，要写到具体单位或角色。

## 8. 图表清单与待确认章节（长文档的两个必备件）

### 8.1 图表清单

长文档通篇是字，一定显得空泛。动笔前按文档类型定要出哪些图，写成"编号 + 图名 + 所在章节 + 要表达的关系"，边写边出图，交付前清点。

| 文档类型 | 至少要有的图 |
| --- | --- |
| 总体方案 / 技术方案 | 外部关系图（本系统与外部系统、合作方、上级平台的边界与数据往来）、端到端业务流程图（原始数据到最终交付物）、总体架构与系统组成图、数据/产品对象谱系图（层级与派生关系）、任务状态与异常处理流程图、数据存储-编目-归档-分发关系图、运行监控与质量控制（含人工复核环节）关系图 |
| 需求规格 / 详细设计 | 角色或用例图、业务流程图、模块结构与依赖图、E-R 图（对象→表、关系→字段/外键）、接口时序图、部署与网络分区图 |
| 实施方案 | 进度甘特或里程碑图、组织与责任矩阵、数据迁移流程图（含校验与回退分支）、测试与上线切换流程图 |
| 验收方案 | 验收流程图、指标-方法-材料对应关系表、问题处置与复测流程 |
| 可研 / 建议书 | 建设内容框图、投资构成图、实施进度图、绩效指标与验收对应表 |

图的判定标准跟文字一条：**能不能替代一段空话**。常见废图：只有几个框没有连线含义、图名写"系统架构"但看不出层次、图里放整句形容词、序号与正文引用对不上。

交付时附图表清单，未出图的标"待出图"，不要用空占位或与内容无关的示意图糊过去。

### 8.2 待确认事项章节

写作过程中冒出的不确定项会越来越多，散在各章节里就直接变成"待定/视情况"（评审扣分项）。统一汇总到**文末独立章节**（章号按文档结构定，如总体方案放第 15 章；也可做成附录），每项至少五列：

| 序号 | 待确认内容 | 影响章节 | 责任方 | 需取得的资料 | 最迟确认节点 |
| --- | --- | --- | --- | --- | --- |
| 1 | 产品等级划分与命名规则的正式评审版 | §5、§10 | 甲方业务部门 | 评审通过的等级定义文件 | 详设启动前 |
| 2 | 外部系统接口字段、状态码与调用方式 | §11 接口设计 | 外部系统厂商 | 接口规格说明书 | 联调前 |
| 3 | 单日数据量、峰值速率、并发任务量 | §12 指标测算 | 载荷/运行方 | 参数表与运行记录 | 定稿前 |
| 4 | 网络与数据密级、跨区交换方式 | §13 安全保障 | 甲方信息安全部门 | 等级保护定级与安全方案 | 定稿前 |

配套规则：

- 正文里对应位置只写"该参数取值见第 X 章待确认事项第 N 项"，不写"待定""视情况"。
- 每项必须有**责任方**和**最迟确认节点**——没有这两列的待确认表等于把问题推给读者。
- **能问用户就当场问**：这一项是否挡住当前章节的编写？挡住 → 先问（一次最多 3 个），问不到再挂本表并跳过该节；不挡写现状与方案框架 → 直接写不依赖它的内容，参数进本表。要等外部厂商、等上级批文这类问不动的，才安静留在表里。
- **不许用空话占位**：缺参数时不得写推测数值，也不得用"能力/流程/参数项/测算方法"重新包装一遍充数（判据见 `anti-slop.md` §1），正文只保留有来源的事实和本表的引路句。
